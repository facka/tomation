Tomation Documentation

Get Started & Installation #

Tomation is a browser automation framework with a structured DSL for writing readable UI tests. You author scripts with TypeScript-powered autocomplete, compile them to portable JSON, and run them in the browser via a lightweight extension.

Follow these steps to go from zero to running your first test:

Step 1: Install the Browser Extension

Install the Tomation extension from the Chrome Web Store. This is the runtime that executes your compiled tests directly in the browser with visual step-by-step feedback.

Step 2: Install the Tomation CLI

Install the CLI globally so you can use the tomation command from anywhere: 

npm install -g @tomationjs/compiler

Step 3: Scaffold a New Project

Create an empty folder for your tests and run tomation init to generate a starter project with example POM files, tests, and automations: 

mkdir my-tests && cd my-tests
tomation init
npm install

This creates a ready-to-use project structure: 

my-tests/
├── tomation.config.ts   # Project configuration
├── package.json         # Dependencies (@tomationjs/dsl, @tomationjs/compiler)
├── pom/                 # Page Object Model files (element locators + tasks)
│   ├── login.pom.ts
│   ├── todo.pom.ts
│   └── navigation.pom.ts
├── tests/               # Test files
│   ├── login.test.ts
│   ├── todo.test.ts
│   └── navigation.test.ts
└── automations/         # Parameterized workflows
    └── todo.automation.ts

Step 4: Compile and Run

Compile your DSL files into a .tomation.json file, then load it in the browser extension: 

tomation compile

Open the Tomation extension side panel in Chrome, load the generated JSON file, navigate to your app, and run your tests.

Tomation CLI #

The Tomation CLI compiles your TypeScript POM, test, and automation files into a single .tomation.json file that the browser extension can load and execute. The output file name is derived from the meta.name field in your configuration.

Installation

Install the CLI globally to use the tomation command directly: 

npm install -g @tomationjs/compiler

Init

Scaffold a new Tomation project with example POM files, tests, and automations: 

tomation init

Compile

Run the compile command from your project directory to produce the .tomation.json output file: 

tomation compile

Watch Mode

Use watch mode for live recompilation during development. The CLI will automatically recompile whenever your source files change: 

tomation watch

Configuration File #

Every Tomation project requires a tomation.config.ts file at the root of the project. This file tells the compiler where to find your source files and how to name the output.

Available configuration fields:

Field Description
meta.name Project name — used for the output filename
meta.urls Array of URLs where tests can run
pom Path to the POM files directory
tests Path to the test files directory
automations Path to automation files directory (optional)
data Path to data files directory (optional)
baseUrl Base path for relative URL resolution

Full configuration example:

// tomation.config.ts
export default {
  meta: {
    name: 'My App Tests',
    urls: ['http://localhost:3000'],
  },
  pom: './pom',
  tests: './tests',
  automations: './automations',
  data: './data',
  baseUrl: './',
}

Element/Locators Builder API #

Tomation uses a fluent builder API to declare element locators. The core pattern is is.TAG.where(matcher).as('Label') — you pick an HTML tag, apply one or more matchers to narrow the selection, and give it a human-readable label.

Basic Element Declaration

Any uppercase HTML tag name works with the is builder: is.INPUT, is.BUTTON, is.DIV, is.FORM, is.SELECT, etc. 

import { is, idIs, innerTextIs, classIncludes, placeholderIs, nameIs, typeIs } from '@tomationjs/dsl'

const submitButton = is.BUTTON.where(idIs('submit-btn')).as('Submit Button')
const emailInput = is.INPUT.where(nameIs('email')).as('Email Input')
const heading = is.H1.where(innerTextIs('Welcome')).as('Page Heading')

Scoping with childOf

Use .childOf(parent) to scope the element search within a parent element. This is useful when you have multiple elements with the same matcher on the page but need to distinguish them by their container. The .childOf() and .where() methods can be chained in any order. 

const loginForm = is.FORM.where(idIs('login-form')).as('Login Form')
const submitButton = is.BUTTON.where(innerTextIs('Submit')).childOf(loginForm).as('Login Submit')

const signupForm = is.FORM.where(idIs('signup-form')).as('Signup Form')
const signupSubmit = is.BUTTON.where(innerTextIs('Submit')).childOf(signupForm).as('Signup Submit')

XPath Elements

For complex selectors that go beyond tag + matcher combinations, use the Element() function with an XPath expression: 

import { Element } from '@tomationjs/dsl'

const alert = Element('//div[@role="alert"]').as('Alert Box')
const thirdRow = Element('//table/tbody/tr[3]').as('Third Row')

Navigate (Relative DOM Traversal)

Use .navigate(path) to enable relative DOM traversal from an anchor element. First, the anchor element is located using the standard tag + matcher logic, then the runtime traverses the DOM following the comma-separated path of navigation steps to reach the final target element. This is useful for locating elements that lack unique identifiers but are positioned predictably relative to an identifiable anchor.

Supported navigation steps:

StepDescription
parentTraverses to the parent element
child[n]Traverses to the nth child element (1-based)
firstChildTraverses to the first child element
lastChildTraverses to the last child element
nextSiblingTraverses to the next sibling element
prevSiblingTraverses to the previous sibling element
sibling[n]Traverses to the nth sibling (1-based, via parent's children)

Usage examples:

import { is, idIs, innerTextIs } from '@tomationjs/dsl'

// Navigate from an anchor element to a nearby target
const target = is.DIV.where(idIs('anchor')).navigate('parent,child[2]').as('Target')

// Combine with childOf for scoped anchor + navigation
const container = is.DIV.where(idIs('section')).as('Section')
const content = is.SPAN.childOf(container).where(innerTextIs('Header')).navigate('nextSibling').as('Content')

The .where() method accepts matcher functions that narrow down element selection by matching on attributes, text content, position, or state. You can combine multiple matchers to create precise locators.

valueIs(value)Element value propertyis.INPUT.where(valueIs('hello'))

User Functions: Click, Type, Select #

User functions simulate real user interactions with the page. They operate on element locators declared via the builder API and form the core of every test step.

Interaction Functions

Click(element) — Click on an element. Works with buttons, links, checkboxes, or any clickable target.

Type(value).in(element) — Type text into an input or textarea field.

TypePassword(value).in(element) — Type a password into an input. The value is masked in logs for security.

Select(value).in(element) — Select an option from a dropdown (<select>) element by its visible text. 

import { Click, Type, TypePassword, Select } from '@tomationjs/dsl'

// Click a button
Click(submitButton)

// Type into an input field
Type('user@example.com').in(emailInput)

// Type a password (value masked in logs)
TypePassword('s3cretP@ss').in(passwordInput)

// Select a dropdown option
Select('Admin').in(roleDropdown)

Save to Context #

Save functions capture runtime values from the page and store them in a shared context object. Saved values can be referenced later in the same test using the {{ctx.keyName}} interpolation syntax.

SaveText(element).as('key') — Save the element's text content to context.

SaveAttribute(element, 'attr').as('key') — Save a specific attribute value from the element.

SaveValue(element).as('key') — Save an input element's current value.

Save(expression).as('key') — Save a computed expression or literal value to context. 

import { SaveText, SaveAttribute, SaveValue, Save } from '@tomationjs/dsl'

// Save the text content of an element
SaveText(welcomeMessage).as('greeting')

// Save a specific attribute
SaveAttribute(profileLink, 'href').as('profileUrl')

// Save an input's current value
SaveValue(searchInput).as('lastSearch')

// Save a computed expression
Save('2024-01-15').as('targetDate')

// Reference saved values later in the test
Type('{{ctx.greeting}}').in(noteInput)

Date Helpers #

Date helpers generate formatted date strings relative to the current date. They are useful for filling date inputs with dynamic values that stay correct over time. All helpers accept an optional format string (default: YYYY-MM-DD).

Available helpers: today(), tomorrow(), yesterday(), nextWeek(), lastWeek(), nextMonth(), lastMonth(), firstDateOfMonth(offset), lastDateOfMonth(offset). 

import { today, tomorrow, yesterday, nextWeek, lastWeek, nextMonth, lastMonth, firstDateOfMonth, lastDateOfMonth } from '@tomationjs/dsl'

// Default format: YYYY-MM-DD
Type(today()).in(dateInput)
Type(tomorrow()).in(dueDateInput)
Type(yesterday()).in(startDateInput)

// Week and month offsets
Type(nextWeek()).in(scheduledInput)
Type(lastMonth()).in(reportDateInput)

// Custom format
Type(today('DD/MM/YYYY')).in(localeDateInput)
Type(nextWeek('MM-DD-YYYY')).in(usDateInput)

// First and last date of month (offset: 0 = current, 1 = next, -1 = previous)
Type(firstDateOfMonth(0)).in(periodStartInput)
Type(lastDateOfMonth(0)).in(periodEndInput)
Type(firstDateOfMonth(1)).in(nextPeriodStartInput)

Keyboard Actions #

Simulate key presses on the focused element or a targeted element. Use shortcuts for common keys, or the generic PressKey / Press for any key with modifier support.

Shortcut functions (press on the currently focused element):

FunctionKey dispatched
PressEnter()Enter
PressTab()Tab
PressEsc()Escape
PressSpace()Space
PressUp()ArrowUp
PressDown()ArrowDown
PressLeft()ArrowLeft
PressRight()ArrowRight

Generic functions:

FunctionDescription
PressKey(key, options?)Press any key on the focused element. Accepts optional modifiers.
Press(key, options?).in(element)Press a key on a specific targeted element.

Modifiers — the optional options object:

{ ctrl?: boolean, alt?: boolean, meta?: boolean, shift?: boolean }

import { PressKey, Press, PressEnter, PressTab, PressEsc } from '@tomationjs/dsl'

// Shortcuts — press on focused element
PressEnter()
PressTab()
PressEsc()

// Generic — any key with modifiers
PressKey('a', { ctrl: true })       // Ctrl+A (select all)
PressKey('s', { meta: true })       // Cmd+S (save)
PressKey('Delete')                  // Delete key

// Targeted — press on a specific element
Press('Enter').in(searchInput)
Press('ArrowDown', { alt: true }).in(dropdown)

Test Data & Fake Generators #

Define reusable data templates with Data() and generate realistic random values using Fake generators. Each test run produces fresh values — no more hardcoded strings.

Defining a Data Template

Create a .data.ts file and use Data() to declare a template with static values and Fake generator calls: 

// data/user.data.ts
import { Data, Fake } from '@tomationjs/dsl'

const user = Data({
  name: Fake.fullName(),
  email: Fake.email(),
  phone: Fake.phone({ country: 'US' }),
  dob: Fake.dateOfBirth({ minAge: 18, maxAge: 65, format: 'MM/DD/YYYY' }),
  role: Fake.oneOf(['Admin', 'Editor', 'Viewer']),
  address: Fake.address(),
  id: Fake.uuid(),
  notes: Fake.sentence(),
})

export default user

Using Data in Tests

Import the data template and reference its properties directly. The compiler resolves them to {{data.templateName.property}} tokens, and the runtime generates fresh values each run: 

// tests/registration.test.ts
import { Test, AssertHasText } from '@tomationjs/dsl'
import user from '~/data/user.data'
import Form from '~/pom/registration.pom'

Test('Register with generated data', () => {
  Form.fillForm({
    name: user.name,
    email: user.email,
    phone: user.phone,
  })
  Form.submit()
  AssertHasText(Form.message, 'Registration successful')
})

Reproducible Data with Seed

Pin a seed to generate the same values every run — useful for reproducing failures: 

const user = Data({
  name: Fake.fullName(),
  email: Fake.email(),
}, { seed: 42 })  // Same values every run

You can also pin/unpin seeds from the extension UI in the Test Data panel without editing code.

Configuration

Add a data property to your tomation.config.ts to specify where data files are located: 

export default {
  meta: { name: 'My App', urls: ['http://localhost:3000'] },
  pom: './pom',
  tests: './tests',
  data: './data',  // ← data files directory
  baseUrl: './',
}

Enums & Const Maps #

For hardcoded data that doesn't change between runs, use TypeScript enum declarations or const object maps. The compiler resolves member references at build time into their literal string values.

Using an enum:

// data/skills.enum.ts
enum TechSkill {
  JavaScript = 'JavaScript',
  TypeScript = 'TypeScript',
  Python = 'Python',
  React = 'React',
  NodeJS = 'Node.js',
}

export default TechSkill

Using a const map:

// data/skills.ts
const TechSkill = {
  JavaScript: 'JavaScript',
  TypeScript: 'TypeScript',
  Python: 'Python',
  React: 'React',
  NodeJS: 'Node.js',
} as const

export default TechSkill

Using in tests or automations:

import TechSkill from '~/data/skills.enum'
// or: import TechSkill from '~/data/skills'

// Resolved at compile time to the literal value "TypeScript"
Select(TechSkill.TypeScript).in(skillsDropdown)

Both forms work the same way: the compiler reads the enum or const map at build time and replaces TechSkill.TypeScript with "TypeScript" in the output JSON. This keeps your test code readable while avoiding magic strings.

Conditionals in Tasks #

Tasks support conditional logic using standard if statements. The condition must reference a parameter from the task's params object. Steps inside the if block only execute when the condition is met at runtime.

Supported condition patterns:

PatternMeaning
if (param)Truthy — execute when param is provided / non-empty
if (!param)Falsy — execute when param is absent / empty
if (param == true)Boolean truthy — same as if (param)
if (param == false)Boolean falsy — same as if (!param)
if (param === 'value')Equals — execute when param matches a specific string
if (param !== 'value')Not equals — execute when param does not match

Example — optional steps based on boolean params:

import { Task, Click } from '@tomationjs/dsl'

const applyFilters = Task((params: { unreviewed?: boolean, archived?: boolean }) => {
  const { unreviewed, archived } = params
  Click(clearAllButton)
  if (unreviewed == true) {
    Click(unreviewedCheckbox)
  }
  if (archived == true) {
    Click(archivedCheckbox)
  }
}).as('Apply Filters')

Example — branching on a string param:

const selectRole = Task((params: { role: string }) => {
  const { role } = params
  if (role === 'admin') {
    Click(adminRadio)
  }
  if (role === 'viewer') {
    Click(viewerRadio)
  }
}).as('Select Role')

Note: Only parameters destructured from params can be used in conditions. else blocks are not supported — use a separate if with the negated condition instead. Both == and === are accepted.

Assertions #

Assertion functions verify that the page is in the expected state after user interactions. They fail the test immediately if the condition is not met.

AssertExists(element) — Asserts that an element exists in the DOM and is visible.

AssertNotExists(element) — Asserts that an element does NOT exist or is not visible.

AssertHasText(element, expectedText) — Asserts that an element's text content matches the expected string. 

import { AssertExists, AssertNotExists, AssertHasText } from '@tomationjs/dsl'

// Verify element exists
AssertExists(Login.submitButton)

// Verify element does not exist (e.g., error message hidden)
AssertNotExists(Login.errorMessage)

// Verify text content
AssertHasText(Login.message, 'Login successful')

Tests #

Tests are declared using the Test(name, callback) function in *.test.ts files. Each test has a descriptive name and a callback containing the sequence of interactions and assertions that make up the test scenario.

Test File Structure

Test files live in the directory specified by the tests field in your tomation.config.ts. Each file imports the Test function from the DSL along with any interaction or assertion functions needed, and imports POM elements to interact with. 

// tests/login.test.ts
import { Test, Click, AssertExists, AssertHasText } from '@tomationjs/dsl'
import Login from '~/pom/login.pom'

Test('Login with valid credentials', () => {
  Login.fillCredentials({ username: 'admin', password: 'secret' })
  Login.submit()
  AssertHasText(Login.message, 'Login successful')
})

Test('Login shows error on empty submit', () => {
  Click(Login.submitButton)
  AssertHasText(Login.errorMessage, 'required')
})

Compilation & Execution

When you run npx tomation compile, the compiler processes all *.test.ts files in the configured tests directory, resolves POM imports, and includes the compiled tests in the .tomation.json output file.

Tests are run interactively via the Tomation browser extension. Load the compiled .tomation.json file in the extension panel, select one or more tests, and execute them against the live page. The extension renders real-time results including pass/fail status and step-by-step logs.

Display Labels

Tests and automations are displayed in the extension using the format sourceFile: label. The sourceFile is the relative path from the project root with the tests/ or automations/ prefix removed and file extensions stripped. For example, login: Login with valid credentials or auth/login: Login with valid credentials for tests in subfolders.

Automations #

Automations are like Tests but with typed parameters that are filled in at runtime via a form in the browser extension. Instead of hardcoding values, you declare a params object with typed fields — the extension generates a form for each parameter, letting you reuse the same procedure with different inputs each time.

Declaration

Declare automations using the Automation(name, callback) function in *.automation.ts files. The callback receives a typed params object whose shape determines the form controls shown in the extension. 

// automations/todo.automation.ts
import { Automation, AssertExists, AssertHasText, SaveText } from '@tomationjs/dsl'
import Todo from '~/pom/todo.pom'

Automation('Add Todo Item', (params: { item: string }) => {
  Todo.addItem({ text: params.item })
  AssertExists(Todo.firstItem)
  SaveText(Todo.firstItemText).as('savedItem')
  AssertHasText(Todo.firstItemText, params.item)
})

Parameter Types

The TypeScript type of each parameter field controls which form input is rendered in the extension panel:

TypeForm InputNotes
stringText inputFree-text field
numberNumber inputCoerced to parseFloat
DateDate pickerSent as ISO YYYY-MM-DD
'a' | 'b' | 'c'Select dropdownConstrained options

Optional parameters use ? in the type definition and won't block execution if left empty in the form.

Configuration

Automation files live in the directory specified by the automations field in your tomation.config.ts. Ensure the field is set so the compiler includes your automation files in the output: 

// tomation.config.ts
export default {
  meta: { name: 'My App', urls: ['http://localhost:3000'] },
  pom: './pom',
  tests: './tests',
  automations: './automations',
  baseUrl: './',
}

POM Files #

Tomation uses the Page Object Model (POM) pattern to organize element locators and reusable tasks into dedicated files. Each page or section of your application gets its own *.pom.ts file that declares elements, reusable tasks, and exports them as a single default object.

Folder-Based Namespacing

Organize POM files in folders to avoid naming conflicts. Subfolders create namespaces when imported — for example, import Login from '~/pom/login.pom' imports the default export from that POM file. As your project grows, use folders to group related pages (e.g., pom/auth/login.pom.ts, pom/auth/signup.pom.ts).

The Export Default Pattern

Each POM file exports a default object containing all its declared elements and tasks. This makes imports clean and gives consuming test files a single namespace to work with. 

// pom/login.pom.ts
import { is, idIs, Task, Type, TypePassword, Click } from '@tomationjs/dsl'

const usernameInput = is.INPUT.where(idIs('username')).as('Username')
const passwordInput = is.INPUT.where(idIs('password')).as('Password')
const submitButton = is.BUTTON.where(idIs('login-btn')).as('Submit')
const message = is.DIV.where(idIs('message')).as('Message')

const fillCredentials = Task((params) => {
  const { username, password } = params
  Type(username).in(usernameInput)
  TypePassword(password).in(passwordInput)
}).as('Fill Credentials')

const submit = Task(() => {
  Click(submitButton)
}).as('Submit')

export default { usernameInput, passwordInput, submitButton, message, fillCredentials, submit }

Tests and automations can then import the POM and use its elements and tasks directly: 

import Login from '~/pom/login.pom'

// Use elements
Click(Login.submitButton)

// Use tasks
Login.fillCredentials({ username: 'admin', password: 'secret' })
Login.submit()

Generate POM Files with the Lab

Instead of writing POM files by hand, you can use the Lab tab in the Tomation extension to generate them automatically using AI. The Lab lets you visually inspect page elements and produces complete .pom.ts files — including element declarations and reusable Task functions.

How it works:

  1. Configure your AI provider — Set up your API key (OpenAI, Anthropic, Gemini, or a custom endpoint) in the Lab's AI Configuration section.
  2. Choose a context mode — Select "Full HTML" to send the entire page, or "Inspect Element" to pick specific components.
  3. Select elements — In Inspect Element mode, click on page elements to build a multi-node selection (up to 20 nodes). Each selected element is shown in a mini-editor where you can review its HTML.
  4. Review and edit — The Code Viewer shows the HTML that will be sent to AI. You can edit it directly before generating.
  5. Generate — Click "Generate POM" and the AI produces a complete .pom.ts file with element locators and Task functions for common user workflows.

Privacy: Email addresses, passwords, and personally identifiable information are automatically stripped from the HTML before sending to any AI service.

Tip: The Lab generates production-ready POM files using the same DSL functions documented above (is, Task, where matchers). You can use the generated output as-is or refine it to match your project's naming conventions.
